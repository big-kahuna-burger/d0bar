Sending to Dash0

      

        “Run a fake checkout” emits a nested trace and log records from the page's
        own SDK — five child spans around real requests, one of them a 503 that ends the span
        with an error status, and DEBUG/INFO/WARN/ERROR logs correlated to the span that was
        current. The requests are genuine, so tier 1 records resource entries for them and tier
        4 has something to join against; a generator that emitted spans without traffic would
        look right in Dash0 and prove nothing about d0bar.
      

      
Why some rows say NONE, and why that is right

      

        d0bar reads trace context; it never adds any. The worker parses
        traceparent off each request and nothing more — injecting a header would be
        the toolbar modifying the traffic it reports on. So a row shows a trace id only if the
        application put one there.
      

      

        “Run a fake checkout” therefore sets traceparent itself, by
        hand, from the active span. No instrumentation-fetch is installed: that
        patches fetch, and a page that patched fetch could not be used
        to show that d0bar does not. “Make some requests” sends none, so those rows
        stay untraced — a panel where every row was traced would be hiding the case you most
        need to see.
      

      

        The token is never in page script. The page exports to
        /otlp/v1/traces and /otlp/v1/logs on this origin, and the
        fixture server forwards to Dash0 — the part a collector plays in a real deployment.
        Start the server with those in its environment:
      

      
DASH0_INGRESS=https://ingress.<region>.aws.dash0.com \
DASH0_TOKEN=<your token> \
DASH0_DATASET=default \
node bench/fixtures/server.mjs

      

        Unset is the ordinary case and is not faked: /otlp/* answers 501 with what
        to set, the badge above says so, and nothing pretends telemetry was delivered.

What you will see, and what you will not

      

        

          Tier
          On a real page
        

        

          1 — requests, vitals
          
            Full. Read from the browser's own entries, so third-party traffic shows up too.
          
        

        

          2 — service worker
          
            Off, and the panel says so. A service worker script must be
            same-origin as the page it controls, so one served from this dev server cannot be
            registered onto someone else's site — no configuration changes that. Requests read
            as untraced. This is the degraded path working correctly, not a failure. To see tier
            2 live, use this page, or serve d0bar from your own origin.
          
        

        

          4 — OpenTelemetry
          Live only if the page already runs an OTel web SDK. Most do not.
        

      


      
When it will not load at all

      
    
        
  • 
          Content-Security-Policy. Most large sites block a script from an
          origin they did not list. Nothing appears and the console says why. Try a smaller
          site, or your own app in development.
        
    • 
        
  • 
          HTTPS pages. A page on https: will not load a script
          over http:. Use this against a local or http: page.
        
    • 
        
  • 
          Server not running. This page is served by it, so if you are reading
          this it is up.
